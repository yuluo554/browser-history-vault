## 3. M6 发布执行清单（顺序固定）

### 阶段 A：发布前（全部在本地完成，未推送）

1. **历史 = 工作树核对**：`git status` / `git log --oneline | head` / `git rev-list --count HEAD` 三连——确认要发布的东西真在历史里（只提交了部分改动是最常见的发布期事故）；
2. **代码冻结**：版本四处一致（tag / `pyproject` 动态读取的 `__version__` / `README` 状态行 / Release 名）；README 状态行由"开发中"改为已发布态；
3. **干净 clone 复核**（便宜且早，别全押给 CI）：`git clone --no-local <repo> <tmp>` + 全新 venv + 全量 pytest + 按 README 逐条跑；本机已装过 extra 的"假绿"在这里暴露；
4. **脱敏四步 + 产物扫描 + 提交元数据**：
   - 提交邮箱逐条核对为 GitHub noreply；annotated tag 的 tagger 邮箱同样核对；
   - 入库文件扫描本机绝对路径（含 `plan/` 与所有留档），命中即掩码；
   - 扫描器词面**运行时实算**、源码与留档**零词面**；留档里解释误报机制时也不许复述词面；
   - **"纯本地/零上传"的措辞与审计范围对齐**（当前 README 的措辞是"本项目代码不含任何网络调用路径"，对应的四层审计只落地了 ①③；②④ 在发布期补齐后才升级措辞）；
5. **源码包自足**：`MANIFEST.in` 白名单把 `data/` 下需要随源码走的内容打进 sdist；验证 = 解包附件 → 安装 → **从解包目录之外**跑 CLI（在仓库根跑会侥幸通过，测不出"包内推导"）；
6. **手工源码包（不用 GitHub 自动 Source code 包）**：
   ```
   git archive --format=tar --prefix=browser-history-vault-<tag>/ <tag> | gzip -9n > <附件名>.tar.gz
   sha256sum <附件名>.tar.gz > SHA256SUMS
   ```
   同 tag 重复构建 sha256 相同（可复算）——自动 zipball 做不到这一点；
7. **首次实跑 CI 的对账预期**：建仓 → push → 等 CI。**预算"首推至少一轮诊断"**；四矩阵同点全红 = 步骤接线缺陷（不是平台差异）；push 事件数 = run 数，tag push 与 branch push 各一条 run（同 sha 两条合法）。

> **发布顺序：先 private 跑 CI，绿了再切 public**（顺序反了代价高一个量级：公开后再改历史/改附件要处理缓存与已传播的引用）。

### 阶段 B：发布动作

8. 写 `plan/RELEASE-M6.md`（**两栏**：tag 时点事实 / 发布后追加事实），并在 `plan/00` 回写 M6 行；
9. 打 **annotated tag**（`git tag -a v0.1.0 -m ...`），tag 树必须已含：发布留档、已翻转的 README 状态、已翻转的 M6 行；
10. `gh release create <tag> <附件> SHA256SUMS --notes-file <notes>`；核验 `gh release view <tag> --json isDraft,assets,tagName`（**发布动作完成 ≠ 资产就位**：上传偶发半失败，核一发 API 才算闭环）；
11. **发布终态自检门**（`tools/check_release.py`）：
    - 离线模式：留档两栏是标题行且无占位符 / 版本一致 / 状态已翻转 / 附件校验和块可机读；
    - `--online` 模式：仓库公开可访问 / tag 指向与登记相符 / 该提交 CI **逐 job** success / Release 非 draft / 附件集合 == 登记载荷 + 校验和伴随文件 / **逐个附件下载回来重算 sha256**；
    - **门自己也要变异验证，且检查项数要与变异组数对账**（没被证伪过的检查项 = 潜在假门）；存在性检查 ≠ 覆盖性检查；
    - **刻意不进 CI**：判据 = "这道门在当前时点本来就该红吗"——发布前它必然红，挂进 CI 只会让正常提交红得没有信息量。

### 阶段 C：发布物本体复核（能证伪里程碑自述）

12. **三步走**：
    1. `gh release download`（**在仓库目录内跑**）真下载附件；
    2. `sha256sum -c SHA256SUMS` + 与留档件 `cmp` 逐位比对；
    3. 附件解包树 vs `git archive <tag>` 解包树 `diff -r`（**逐字节同源**的正面证明）；
13. **中立目录 + 全新 venv**：从**解包树**里逐条走 README（主打路径真跑）；冻结态自检断言数据目录解析到解包树之内；
14. **发布后复核**：GitHub 全新 clone（另一台/另一目录）跑一遍；`topics` / `description` 与 README 定位一致；**匿名无凭据通道**复核（owner 视角看不见的一关）。

## 4. 发布留档的两栏纪律（`plan/RELEASE-M6.md`）

| 栏 | 内容 | 纪律 |
|---|---|---|
| **tag 时点事实** | tag 名与目标提交、CI run id 与结论、附件名与 sha256、登记载荷清单、DoD 逐项打勾 | **只写实测到的**；未跑的项留 ⬜ 并说明原因，**不留空、不预填** |
| **发布后追加事实** | 真下载复核结果、匿名通道复核、下载 URL 缓存收敛过程、缺陷处置（若需要） | 追加事实**不是**回填美化；tag 之后才存在的结论必须分栏写清"这是 tag 后的事实" |

**配套三条**：

1. **已发布窗口关闭后的缺陷处置**：不重写 tag；走追加提交 + "tag 后追加事实"栏登记；判据是"读者会不会拿到错结论"；
2. **自指规避**：附件自身的 sha256 不写进附件内部任何文件（写入即永不成立）；绝对值放 Release notes 与留档；
3. **历史文档保留原措辞**：措辞升级（如"本地等价校验"→"CI 已跑"）只能**追加补记**，不得回填改写原文。

## 5. 例外与"刻意不做"清单（逐条带理由）

| 项 | 处置 | 理由 |
|---|---|---|
| `config.json` 不被 README 路径门禁要求存在 | 列入 `tests/test_readme_gate.py` 的 `PATH_CHECK_EXCEPTIONS` | 它是**用户按样例复制出的个人口径文件**，按隐私设计要求不入仓 |
| `tools/check_release.py` 不进 CI | 刻意 | 发布前它本来就该红（tag/Release 还不存在），挂 CI 只会让正常提交红得没有信息量 |
| `data/` 不进 wheel/sdist 的安装面（sdist 需白名单显式带上） | 刻意 + 显式声明 | 本项目是源码优先交付；数据底座由仓库树提供，运行期路径始终打印 |
| 报告"零外链"取从严档（连 `//` 都判红） | 刻意 | 本项目报告不含任何"内容链接"，从严档才能守住"断网可开"的强声明；代价是文案/注释/CSS 里不许出现 `//` |
| 不预置空跑的生成器与基准（M0 只落计划） | 刻意 | 空分母会伪装成"通过"；`not_enabled` 与"跑了没过"必须可区分 |
| 名称 `bhvault` 而非 `vault` | 刻意 | 避免与 HashiCorp Vault 的 CLI 同名互相遮蔽；题面 §5 招牌动词表的命令名按此同步（v1.1） |

## 6. M6 的"DoD 打勾纪律"

- 每个 ✅ 都要能回答**"在哪验的"**——同一句"exe/CLI 正常"在仓库根与在中立目录是**两个结论**；
- 发布期发现的缺陷：修完要**加回归测试**，并在留档里写清根因与修复提交；**首跑失败照录不抹除**；
- **CI 绿**只有在真实 run 存在时才写；无远端期间一律写"本地等价校验（未接远端，CI 待首推验证）"并列出替代证据；
- 收尾必须运行 `tools/check_release.py` 且**无 FAIL**（WARN 允许，但每条 WARN 要在留档里给处置）。
